# GameHub 2.0 交互与模块化架构

## 结论

GameHub 当前不是单纯的视觉问题，而是页面、游戏逻辑、用户状态和运营配置混在多个 HTML 文件中。后续不再逐页复制样式，而是建立统一的应用壳、游戏协议、状态管理和设计令牌。

## 当前问题

- 共有 71 个 HTML 页面，68 个页面引用公共设计系统，但大量页面仍然使用独立的内联样式和脚本。
- 页面之间重复实现导航、按钮、卡片、弹窗、加载态和移动端布局。
- `runtime/games/` 已有部分游戏模块，但轻量游戏仍然直接把玩法写在页面中。
- 页面状态、用户数据、排行榜、奖励和视觉反馈没有统一事件协议。
- 公共样式只能改变颜色和表面，不能改变页面的信息层级和交互流程。
- 排行榜等页面存在大体量内联代码，修改时容易出现脚本泄漏到页面正文的问题。

## GameHub 2.0 产品结构

```text
应用壳
├── 顶部状态栏：品牌、导航、玩家资产、在线状态
├── 页面路由：大厅、游戏、活动、排行榜、商城、个人中心、管理
├── 内容区域：页面自己的业务模块
└── 全局反馈：Toast、弹窗、音效、粒子、成就、分享

游戏会话
├── 游戏配置
├── 游戏状态
├── 玩家操作
├── 结果结算
└── 统一反馈与数据上报
```

## 目标目录

```text
app/
├── shell/                   # 页面壳、导航、路由和玩家会话
├── ui/                      # 卡片、按钮、弹窗、Toast、响应式布局
├── games/                   # 游戏注册表、协议和旧游戏适配器
├── services/                # 用户、奖励、排行榜、分析和事件总线
└── data/                    # 游戏目录、活动配置和主题配置

runtime/
├── core/                    # 游戏引擎基础能力
├── effects/                 # 音效、粒子、震动
└── games/                   # 已模块化的游戏实现

styles/
├── tokens.css               # 颜色、间距、字体和动效
├── shell.css                # 应用壳
├── components.css           # 通用组件
├── game-hud.css             # 游戏 HUD
└── themes.css               # 游戏主题
```

## 游戏统一协议

每个游戏不再决定自己的页面壳，只负责游戏内容和状态：

```js
const game = {
  id: 'wheel',
  meta: { name: '大转盘', category: '抽奖', accent: '#FF6078' },
  mount(container, context) {},
  start() {},
  handleAction(action, payload) {},
  getState() { return {}; },
  destroy() {},
};
```

`context` 只提供统一能力：配置、玩家、奖励、事件、音效、反馈和数据上报。游戏不能直接操作其他页面的 DOM，也不能自行改写全局导航。

## 统一交互模型

### 大厅

大厅只做三件事：展示正在发生的游戏、展示玩家当前状态、让用户直接进入。游戏卡片必须同时呈现状态、核心数据和入口动作，采用 Figma 参考中的“信息与操作同卡完成”模式。

### 游戏页

每个游戏页固定为：

1. 游戏标题和当前状态
2. 核心玩法区域
3. 当前可执行操作
4. 结果反馈
5. 次数、奖励和进度

### 结果反馈

```text
操作开始 → 锁定操作 → 运行反馈 → 结果结算 → 奖励/失败反馈 → 再来一次或返回大厅
```

## 视觉层级

- 基础层：深色空间、网格、低对比面板。
- 状态层：青色表示实时和可用，绿色表示成功，红色表示风险或失败，黄色表示高价值。
- 操作层：主操作必须在首屏可见，并且只保留一个主要动作。
- 装饰层：霓虹光、粒子、扫描线只能服务状态反馈，不能代替信息层级。

## 迁移顺序

### 阶段一：基础设施

- 建立应用壳、路由、事件总线和游戏注册表。
- 将现有 `design-system.css` 拆为令牌、壳、组件和游戏 HUD。
- 统一加载态、错误态、空态、弹窗和 Toast。

### 阶段二：核心路径

- 重做首页大厅、`play.html` 和 `game-wrapper.html`。
- 首先迁移大转盘、红包雨、九宫格、刮刮乐。
- 用真实游戏状态替换静态展示数据。

### 阶段三：用户和运营

- 排行榜、商城、个人中心共享同一应用壳。
- 管理后台与玩家端分离组件，但共享数据服务和状态协议。
- 修复旧页面内联脚本和裸露脚本输出问题。

### 阶段四：批量迁移

- 休闲游戏按模板批量接入。
- 工具类和测试类页面独立归档，不混入玩家主导航。
- 每迁移一组页面，执行桌面端、移动端、键盘和减少动效回归。

## 完成标准

- 页面不再重复实现全局导航和反馈组件。
- 每个游戏可通过注册表启动、销毁和切换。
- 任何结果都通过统一事件进入奖励、排行榜和分析服务。
- 页面视觉变化来自模块和令牌，而不是在 HTML 中追加覆盖样式。
- 关键路径有冒烟测试，游戏操作有至少一条真实交互回归。
