# 场景补全与视觉验收顺序

## 当前结论

需要先把核心场景补全到“可玩、可对照、可签收”，再继续增加新的扩展场景。

这里的“补全”不是再增加场景编号，而是把已经登记的 21 个参考状态完成到最终视觉交付标准：

- 场景入口、逻辑和状态切换：21/21，已通过；
- 运行时视觉组件结构：21/21，已通过结构探针；
- 当前源码绑定的真实图形截图：0/21，未完成；
- 正式人工视觉签收：0/21，未完成；
- 最终资产签收：8 个仍为灰盒或候选资产，未完成。

所以当前状态是“逻辑场景齐全，视觉场景未完成”，不能把 21/21 解读成“已经完全复刻”。

## 交付顺序

### 第一阶段：办公室首发范围

完成 `office-01` 至 `office-10`，每段必须完成：

1. 当前源码版本的真实窗口截图；
2. 镜头位置、主体比例、光照、材质、背景层次和交互反馈逐帧对照；
3. 差异项返工并重新截图；
4. 人工视觉签收；
5. 对应角色、场景和交互资产从灰盒/候选状态转为可发布状态。

办公室 10 段全部通过后，才具备首发验收资格。

### 第二阶段：城市第二内容包

完成 `city-01` 至 `city-11`，采用与办公室相同的截图、返工、签收和资产门禁。城市内容不能用办公室的签收结果替代。

### 第三阶段：原创扩展

核心 21 段全部通过后，再验收 18 项扩展状态。扩展场景不能替代核心视频复刻，也不能用来掩盖核心视觉差异。

## 当前唯一外部采集阻断

本机 Godot 可执行文件正常，版本为 4.7.1；但当前 macOS 会话没有可用显示输出，`screencapture` 返回无法从显示器创建图像。因此正式视觉截图不能在当前会话中伪造或用无头截图替代。

正式采集入口已经保留源码指纹、窗口图形要求和失败记录。恢复到有可用显示输出的 Mac 会话，或在 Windows 10/11 目标设备上执行采集后，才能继续写入正式视觉证据。

## 放行条件

只有以下条件同时满足，才允许从内部候选进入发布验收：

- 21/21 当前源码截图存在且源指纹一致；
- 21/21 视觉条目人工签收通过；
- 8 个正式资产完成最终权利与质量签收；
- Windows 10/11 目标设备完成候选包 QA；
- 发布方补齐支持邮箱、隐私政策、Steam 身份、年龄分级和运营主体信息。
