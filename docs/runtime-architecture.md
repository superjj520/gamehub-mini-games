# 运行时架构与状态所有权

版本：`0.1.0-dev`

本文把当前灰盒运行时的状态所有权、系统边界和更新顺序固定下来，避免后续进入最终资产生产后由场景脚本互相改写状态。

## 1. 系统边界

| 系统 | 唯一职责 | 可写状态 | 对外事件/接口 |
|---|---|---|---|
| 输入层 | 将键鼠、手柄和后续平台输入归一为动作帧，并在进入规则层前校验有限数值和单帧幅度 | 当前动作帧 | `input` |
| 玩家控制器 | 根据动作帧更新玩家位置、姿态和交互请求 | 玩家位置、姿态 | `player_state_changed`、交互请求 |
| 第三人称镜头 | 根据玩家和镜头输入计算跟随、旋转和遮挡 | 镜头朝向、距离 | `camera_changed` |
| 感知系统 | 根据距离、视野、遮挡和姿态计算 NPC 状态 | NPC 感知状态 | `perception_state` |
| 冲突状态机 | 管理冲突状态、玩家生命、对手生命、近战命中和短时闪避窗口 | 冲突状态、生命、闪避计时器 | `conflict_status`、`player_attack`、`conflict_dodge_success` |
| 任务状态机 | 根据领域事件推进任务、成功、失败和重试 | 任务阶段、任务结果、奖励 | `mission_changed` |
| 交互系统 | 校验距离、条件和输入，并发出一次性结果 | 交互对象状态 | `interaction`、`interaction_blocked` |
| 载具系统 | 管理上下车、驾驶和载具碰撞 | 载具位置、驾驶者 | `vehicle_entered`、`vehicle_exited` |
| HUD 表现层 | 只读取运行时状态并呈现反馈 | UI 可见性和文字 | 不得写任务或库存状态 |
| 存档系统 | 序列化、迁移、备份和恢复已确认的领域状态 | 文件内容、错误信息 | `checkpoint_saved`、`checkpoint_loaded` |
| 会话恢复 | 标记进程是否正常结束 | 会话标记文件 | `session_opened` |
| 启动上下文 | 在主入口与目标场景之间传递一次性场景、恢复开关和存档路径 | 待消费的启动请求 | `request_scene()`、`consume_request()` |

规则：HUD、截图采集和参考验收工具只能读取状态，不能直接推进任务、库存、感知或载具状态。

## 2. 状态所有权

```text
输入帧
  → 玩家控制器 → 玩家位置/姿态
  → 镜头系统   → 镜头快照
  → 感知系统   → NPC 警觉状态
  → 冲突状态机 → 生命/近战/闪避状态
  → 交互系统   → 交互对象状态
  → 载具系统   → 驾驶者/载具位置
领域事件
  → 任务状态机 → 任务阶段/奖励/成功失败
  → HUD        → 只读呈现
  → 音频路由   → 只读反馈
  → 追踪器     → 只读验收证据
领域状态
  → 存档系统   → 版本化文件
主入口选择
  → 启动上下文 → 目标场景一次性消费恢复请求
```

输入帧边界：移动向量最大长度为 `1.0`，镜头单帧输入最大长度为 `240.0`；非有限数值归零，外部回放超出边界则拒绝加载。这个边界只保护输入层，不改变任务规则或平台的具体按键映射。

同一字段只能有一个写入者。场景脚本负责组装依赖、转发事件和重置场景，不直接复制任务规则。

启动器只负责判断目标场景和主存档/备份是否存在，不直接读取领域存档；`LaunchContext` 将场景路径、恢复开关和存档路径作为一次性请求传递给目标场景。`LaunchContext` 与 `SessionJournal` 必须在 `project.godot` 中注册为自动加载单例，保证主场景、测试脚本和异常恢复入口使用同一状态所有者。目标场景在创建 `SaveStore` 前消费请求，存档系统仍是唯一的文件读取者；请求消费后必须清空，避免场景重载或错误切换重复恢复。

## 3. 每帧更新顺序

1. 输入层采集当前动作并写入回放帧。
2. 玩家控制器处理移动、姿态、碰撞和交互请求。
3. 载具系统处理驾驶输入、碰撞和上下车关系。
4. NPC 感知与搜索状态读取玩家快照，产生感知事件。
5. 冲突状态机读取贴身威胁和闪避动作，推进生命、近战命中与短时无伤窗口。
6. 任务状态机消费交互、感知、时间、载具和冲突事件。
7. 存档、追踪器和音频路由消费已确认的领域事件。
8. HUD 和小地图读取最终状态并更新表现。

重试必须先由场景协调器清理库存、交互、冲突、载具和表现状态，再调用任务状态机的重置接口；读取存档则由存档系统返回数据，场景协调器按字段恢复各系统，不能由 HUD 或任务标签自行恢复。办公室和城市存档都必须包含载具位置、朝向、速度和驾驶者状态，读取时由场景协调器恢复后再继续处理上下车输入。存档加载必须先完成版本迁移和字段类型校验；合法 JSON 但位置、镜头、载具、库存或冲突字段类型异常时，存档系统必须安全拒绝并保留可观测错误，不能让篡改数据进入场景状态机。新存档还必须记录内容包标识，场景加载时按当前注册内容包拒绝异包存档；旧版无标识存档只允许由显式传入空标识的非绑定工具调用读取，正式场景必须提供固定内容包标识。

## 4. 扩展约束

- 新任务优先新增内容包字段和领域事件，不在 HUD 中写特殊分支。
- 城市阶段的前置条件和效果必须由内容包声明：`requirements` 负责物品条件，`effects` 负责物品增删、任务标志、追踪事件和音频事件；场景只执行通用解释器，不按任务 id 编写规则分支。
- 内容包必须先登记到 `content/content-pack-manifest.json`，由 `ContentPackLoader.load_registered_pack()` 统一校验和加载；场景不得直接写死内容包文件路径。
- 注册表同时校验内容包身份、类型、路径、启用状态和内容字段，避免把一个合法 JSON 文件误挂到错误的运行时场景。
- 玩法参数必须优先放在内容包的 `runtime` 节点：玩家行走/蹲伏速度、NPC 感知距离/视野/警觉速率、搜索速度和载具驾驶参数都由内容包注入；运行时类只保留安全默认值。
- 城市冲突参数必须放在内容包的 `runtime.conflict` 节点：`damage_per_second`、`dodge_window_seconds` 由冲突状态机读取，`pursuit_speed`、`dodge_cooldown_seconds` 由城市场景读取；冲突状态机只拥有当前生命值、对手生命、冲突状态和闪避计时器，场景不得重新写死调参常量。
- 城市人群和背景交通必须优先由内容包的 `runtime.crowd`、`runtime.traffic` 节点声明路线与速度；场景只负责把已校验的路线实例化为可运行实体，不能把任务专属路线写死在运行时核心逻辑中。
- 办公室出口、上司位置和走廊巡查路线必须由内容包的 `runtime.office` 节点声明；场景只消费已校验的位置和半径，不得通过复制场景脚本来扩展同类办公室任务。
- 新角色通过玩家/NPC控制器的稳定接口接入，不复制场景脚本。
- 新载具实现驾驶接口并接入载具状态事件，不改变任务状态机的存档格式。
- 玩家进入载具后，载具系统必须暂时禁用玩家的 `CollisionShape3D`，退出载具时按进入前状态恢复，避免驾驶者与载具碰撞体互相干扰；该生命周期必须有自动化断言。
- 新平台只扩展输入映射、窗口和导出配置，不改变任务规则。
- 最终资产替换灰盒节点时，必须保留节点名称、交互接口和截图验收锚点，除非验收矩阵同步更新。

## 5. 验证策略

- 系统单测：验证状态迁移、字段边界、存档迁移和非法内容包拒绝。
- 场景集成测试：验证办公室、城市、冲突、载具、暂停和启动恢复。
- 确定性回放：相同输入和种子必须得到相同玩家、镜头和任务结果。
- 视觉验收：每个参考分段绑定参考帧、运行时截图和哈希匹配的对照报告；视觉状态不得由脚本自动改为通过。
- 发布门禁：参考证据、未授权资产和未确认平台配置不得进入运行时发布树。

内容包注册表的最小回归要求：办公室和城市均必须通过注册表加载；注册表与文件 `id` 不一致、未知内容包和非法内容字段必须被拒绝或安全返回空结果。玩法参数还必须覆盖一个越界负向测试。对应测试为 `tests/content_pack_manifest_integration_test.gd`。
