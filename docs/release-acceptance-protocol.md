# 发布验收协议

版本：`0.1.0-dev`

本协议把当前工程从“可以运行”推进到“可以被外部测试、认证和上架”的路径固定为可检查的二值门禁。任何门禁没有证据，都按未通过处理；任何豁免都必须记录批准人、理由、范围和失效时间。

## 1. 四层结论不得混用

| 层级 | 证明什么 | 当前结论 | 允许对外表述 |
|---|---|---|---|
| 运行时健康 | 场景能启动，任务、存档、输入和异常恢复可运行 | 已通过灰盒门禁 | 仅可称为内部开发基准 |
| 参考行为验收 | 21 个分段的输入、事件、失败和重试可重现 | 21/21 灰盒 | 不代表视觉或商业完成 |
| 参考视觉验收 | 每个分段的最终画面、镜头、HUD、动作和音频达到签收标准 | 0/21 视觉通过 | 不得宣称 100% 还原 |
| 发布候选 | 指定平台的导出包在目标设备完成性能、输入、存档、崩溃和商店合规测试 | 未开始 | 不得提交商店 |

## 2. 二值门禁与证据

| 门禁 | 通过条件 | 当前状态 | 证据入口 | 负责人 |
|---|---|---|---|---|
| 产品基线 | 平台、首发范围、品牌、美术方向和预算已签字 | 已通过 | `docs/product-baseline-decision.json` 定稿表 | 产品负责人 |
| 版权边界 | 参考视频、最终资产、字体、音频和第三方组件均有发布许可 | 未通过 | `content/rights-manifest.json`、资产登记 | 权利负责人 |
| 参考媒体证据 | 本地源视频、音频流、分段时间边界和抽帧哈希可复核，且不得进入发布树 | 已通过内部证据校验 | `node scripts/verify_reference_media.mjs`、`reference-evidence/manifest.json` | QA/权利负责人 |
| 运行时 | 全量 Godot 测试、异常退出测试和源指纹稳定 | 已通过灰盒 | `zsh scripts/verify_reference_runtime.sh` | 工程负责人 |
| 行为矩阵 | 21 个分段均有真实输入回放和事件时间轴 | 已通过灰盒 | `docs/reference-acceptance-matrix.md` | QA负责人 |
| 视觉矩阵 | 首发范围内的每个分段逐帧检查通过，且报告指向最终截图哈希 | 未通过 | `reference-evidence/runtime-matrix/` | 视觉负责人 |
| 最终资产 | 角色、动画、环境、载具、UI、音频进入资产生产清单并完成权利签收 | 未通过 | `docs/asset-production-manifest.json` | 美术/音频负责人 |
| 目标设备 | 每个平台的输入、分辨率、帧率、内存、加载和断电恢复通过 | 未开始 | 平台测试包和设备记录 | 发布工程负责人 |
| 隐私与商店 | 隐私政策、用户协议、客服、年龄分级、商店素材和数据安全表完成 | 开发基线已建立，正式材料未通过 | `docs/privacy-data-inventory.md`、`docs/store-submission-checklist.md` | 法务/运营负责人 |
| 回滚 | 已完成本地文件级回滚演练；目标平台与公开版本仍未验证 | 部分通过 | `reference-evidence/release-rollback-rehearsal.json`、发布流水线与回滚演练记录 | 发布工程负责人 |

平台无关的内部候选树可使用 `npm run release:candidate` 生成，并用 `npm run release:candidate:verify` 独立核验。该流程只复制已通过发布树和逐文件清单校验的 `gta-reference-runtime`，进行双次内容摘要一致性检查，并在生成后再次检查候选目录；它不是平台导出包，也不能替代目标设备验收。`npm run verify:evidence-binding` 会确认当前无图形行为回放、事件证据、发布清单、发布准备报告和候选树绑定同一源指纹；历史视觉矩阵如果尚未重新采集，会明确保留为 `unverified`/待重采集，不得通过改元数据伪装成当前截图。

当前已增加 `npm run test:rollback`，用于在临时目录验证两个可追溯 Windows 构建物的文件级切换、失败替换模拟和旧版本恢复。该命令只能证明本地候选文件的回滚逻辑；Steam 分支/Depot、目标设备和公开版本回滚仍需真实平台演练。

`npm run test:reference` 是无头功能与逻辑门禁，并且会调用 `npm run verify:visual-matrix` 校验已保存的图形证据；它不会启动真实图形窗口，也不声称完成视觉采集。真实窗口采集仍必须按《参考视觉采集运行手册》执行，不能把已有文件校验误写成重新采集。

## 3. 固定执行顺序

1. 用户确认产品基线和版权边界。
2. 工程建立首个基线提交；未经确认不得提交或发布。
3. 锁定最终资产清单，原创资产替换灰盒。
4. 在固定构建上完成行为矩阵和视觉矩阵；测试后不得再进行未记录的修改。
5. 针对已确认平台生成导出包，并在目标设备完成输入、性能、存档和异常恢复验证。
6. 完成隐私、客服、商店、年龄分级和回滚材料。
7. 由产品、工程、QA、权利和发布负责人共同签署 Go/No-Go。

正式导出前必须运行 `npm run release:preflight`。该命令会校验产品基线、资产交付门禁、Windows 构建追溯清单、严格 Windows 目标设备 QA 和发布前置条件；当前命令应当阻断。只有产品基线、最终资产、视觉矩阵、平台、权利和发布门禁全部满足后才允许通过。目标设备 QA 的普通结构核验不等于严格人工签收，详见[Windows 目标设备 QA 执行手册](/Users/superjj/gamehub-mini-games/docs/windows-device-qa-runbook.md)。

权利清单中的 `release_scope_ids` 表示该资产被哪个已确认首发范围使用；发布前置检查只检查当前首发范围绑定的条目。`release_candidate_required=true` 表示该条目在其绑定范围内必须具备可发布权利；`false` 表示明确排除在候选发布包之外的内部参考或拒绝资产。未绑定当前范围的城市、第三方或历史候选仍保持阻断状态，但不会被错误算入本次首发的必需资产；真正的最终资产权利仍由资产交付门禁逐槽位校验。

## 4. 证据完整性规则

- 当前源已经变化时，行为回放、日志和导出包必须重新生成并绑定当前身份；旧视觉截图必须保留历史状态，不能只改元数据冒充当前截图。
- 当前源发生变化时，只有在真实图形重新采集后，视觉矩阵才允许绑定新身份；在此之前由当前无图形行为证据证明逻辑回放，视觉门禁继续阻断。
- 视觉采集必须遵循：[参考视觉采集运行手册](/Users/superjj/gamehub-mini-games/docs/visual-capture-runbook.md)。
- 参考视频和抽帧只能作为内部验收输入，不得进入运行时发布树或商店素材。
- 自动化测试只能证明它覆盖的范围；不能用功能测试替代视觉、版权或真机证据。
- 当前主机性能读数不能替代目标设备性能证据。
- 图形服务不可用时，保留 `unverified`，不得用旧截图、无头黑图或人工猜测标记通过。
- 最终一次代码、资产或配置变更后，必须重新生成源指纹和受影响的全部证据。
