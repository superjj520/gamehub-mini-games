# 场景补全与视觉完成门禁

## 结论

需要先补全核心游戏场景，但“补全”分为三个独立层级：

1. 场景状态存在：每个参考分段都有视觉构建器。
2. 场景可玩：真实任务、交互、导航、NPC、载具和 HUD 能驱动场景切换。
3. 场景完成：当前源真实窗口截图、逐段视觉对照、最终资产权利和目标设备验收全部通过。

当前工程已达到前两层的灰盒/候选状态，尚未达到第三层。核心范围是城市 11 段和办公室 10 段，共 21 段；视频之外的原创扩展范围另有 18 项，不能用扩展项替代核心 21 段的视觉验收。报告中的 `scene_matrix` 已按每一段记录构建器、运行时选择器、视觉合同、当前源绑定和下一动作。

## 当前执行顺序

1. 固定核心 21 段的场景状态、任务入口、摄像机、交互目标和失败/重试路径。
2. 将候选角色、环境、城市人群、载具和交互道具逐个挂载到对应场景；候选资产仍标记为未验收，不能冒充最终资产。
3. 在当前源生成 21 段真实窗口截图，绑定当前源指纹。
4. 逐段完成人工视觉对照，确认主体构图、角色姿态、关键物件、光照、HUD 和镜头节奏。
5. 核心 21 段达到视觉通过后，再实现并验收 18 个原创扩展场景。
6. 最后才进入目标 Windows 设备、性能、输入、隐私、商店素材和发布门禁。

## 当前证据状态

运行 `npm run verify:scene-completeness` 可生成 `docs/scene-completeness-report.json`。该报告只证明场景覆盖和运行时选择器是否齐全，不会把灰盒、候选资产或历史截图提升为最终视觉通过。

当前硬门禁仍保持：核心视觉 `0/21`，扩展视觉 `0/18`，正式资产 `8/8` 仍为灰盒/候选未签收，发布状态 `internal_no_go`。因此“场景补全”现在指把每一段推进到可进入、可交互、可复现，并完成当前源画面签收；不是把未验收的盒子继续堆多。
